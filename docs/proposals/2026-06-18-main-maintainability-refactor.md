# 提案：main 分支可维护性重构优化

日期：2026-06-18
状态：提案
面向读者：AI 编码助手、研发、测试、维护者

## 概览

本次工作从 `origin/main` 创建独立分支，在不改变公开 API、输出文件和既有用户行为的前提下，重构高复杂度模块。重点降低 `wsdp.core.pipeline`、算法统一入口、算法注册表和读数入口的阅读成本，让后续新增数据集、算法、模型或训练配置时更容易定位修改点并编写测试。

## 目标

- 将主流程中的加载、缓存、拆分、训练、评估、记录持久化拆成清晰边界，降低单函数认知负担。
- 保持现有测试全绿，并为重构边界补充最小回归测试，证明公开行为不变。
- 不引入新功能、不改变数据格式、不改变默认超参数和输出文件命名。

## 推荐方案

采用“行为锁定 + 分层提取”的保守重构：先用现有测试和新增小型回归测试锁定公开行为，再拆分内部 helper 或小模块。该方案比一次性重写风险低，也比只改命名更能提升长期维护性。

## 备选方案

| 方案 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- |
| 保守重构 | 行为稳定、验证成本可控、适合当前测试基础 | 提升集中在高价值热点，覆盖面有限 | 推荐 |
| 全面重构 | 可一次性统一更多模块风格 | 容易扩大范围，回归成本高 | 不采用 |
| 只做格式与命名 | 风险最低 | 对可扩展性帮助有限 | 不采用 |

## 范围内

- 拆分 `src/wsdp/core.py` 中过长的训练编排逻辑，保留 `pipeline(...)` 对外签名。
- 梳理 `src/wsdp/algorithms/__init__.py` 的统一入口，减少重复参数过滤和分支堆叠。
- 梳理 `src/wsdp/algorithms/registry.py` 的注册、预设、配置解析和执行边界。
- 梳理 `src/wsdp/readers/__init__.py` 的数据集注册与批量读取入口，保持已有数据集名称可用。
- 补充针对上述边界的最小单元或集成测试。
- 更新与本次重构直接相关的文档索引和提案状态。

## 范围外

- 不新增算法、模型、数据集或 CLI 功能。
- 不改变训练指标计算、随机种子策略、默认参数、缓存 key 语义或输出文件格式。
- 不重写模型结构、reader 文件解析细节或 notebook 示例。
- 不处理当前非 main 工作区中的未提交变更。

## 约束

- 必须基于 `origin/main` 的独立 worktree 和新分支完成。
- 每次生产代码修改前必须先明确自动化验证方式；能写测试的行为先写失败测试。
- 公开导入路径保持兼容：`wsdp.pipeline`、`wsdp.algorithms.*`、`wsdp.readers.*`、`wsdp.models.create_model` 不因重构失效。
- `pytest` 必须通过；若新增 lint 或格式化，只能作为辅助验证，不替代测试。
- 不执行远程 push 以外的破坏性 git 操作；最终 push 使用用户已授权的新分支。

## 验收标准

- 前提：安装依赖后的 `origin/main` 基线；操作：运行 `pytest`；结果：基线测试通过，作为重构前行为参照。
- 前提：完成重构；操作：运行完整 `pytest`；结果：全部测试通过，且失败或警告数量不比基线恶化。
- 前提：用户代码仍使用 `from wsdp import pipeline`、`from wsdp.algorithms import denoise, calibrate, normalize, interpolate, extract_features`；操作：执行公开导入和一次最小调用测试；结果：导入路径和返回类型保持兼容。
- 前提：已有算法配置文件包含 `preset`、YAML/JSON pipeline steps 或未知元数据字段；操作：调用配置加载与执行相关测试；结果：解析、跳过未知元数据、错误提示行为保持兼容。
- 前提：训练入口使用缓存开关、模型名或自定义模型路径；操作：通过 mock 或轻量 fixture 覆盖编排分支；结果：仍创建相同类型的输出记录、历史文件、检查点路径和评估流程。
- 前提：reader 收到无效目录、空目录、格式不匹配文件或受支持数据集名称；操作：运行 reader 入口测试；结果：异常、跳过和数据集列表行为保持兼容。

## 阶段计划

### 阶段 1：行为锁定

- 目标：确定重构不能破坏的公开行为。
- 包含：针对核心入口、算法入口、注册表和 reader 入口补充最小回归测试。
- 验证点：新增测试在重构前能覆盖目标行为；若测试揭示既有行为，则按既有行为断言。

### 阶段 2：核心流程拆分

- 目标：让 `pipeline(...)` 保持编排语义，但将内部职责拆到可单独理解和测试的函数。
- 包含：配置解析、缓存读写、数据拆分、模型构造、训练评估、记录输出边界。
- 验证点：核心流程相关测试通过，完整 `pytest` 无新增失败。

### 阶段 3：算法与 reader 入口整理

- 目标：让算法入口和 reader 入口更容易扩展，同时保持对外 API 不变。
- 包含：统一参数过滤、减少分支重复、明确注册表和配置解析职责。
- 验证点：算法、注册表、reader 相关测试通过，完整 `pytest` 无新增失败。

### 阶段 4：收尾与发布分支

- 目标：提交并推送可审阅的新分支。
- 包含：更新 `docs/STATE.md`，整理提交信息，运行最终验证。
- 验证点：工作区干净；提交存在；远端分支可用；最终测试结果记录在回复中。
